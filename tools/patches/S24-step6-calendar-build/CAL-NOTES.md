## How it reads Zoho (same mechanism as the page)
- Only `ZOHO.CRM.API.coql`, `getRecord`, `updateRecord`, `ZOHO.CRM.CONFIG.getCurrentUser`. Page conventions: a timeout on every call (15 s reads, 20 s save), max 2 calls in flight, COQL pages of 200 by `limit/offset` (stop on a short page unless `more_records`, max 10 pages), 204 = no rows, two conditions per COQL group, quotes doubled (`qcode`).
- Who am I: waits for `window.__bdcsUser` (as bdcs-rel does, 20 s), then asks `getCurrentUser` once.
- Query: `select id, Event_Title, Start_DateTime, End_DateTime, All_day, Venue, Description, What_Id, Who_Id, Owner, Recurring_Activity from Events where ((Owner.id = me and Start_DateTime >= 'day-1 00:00') and Start_DateTime <= 'last day+1 23:59:59') order by Start_DateTime asc`. Literals carry the viewer's offset for each boundary (correct across DST). One day either side so all-day records stored in another offset are not lost; results are then cut to the 7 local days.
- Fallbacks (one step each, a timeout stops at once): without the owner clause (filtered here); without `Recurring_Activity`; without `Description`. All fail: the shell's failure wording.
- Repeating meetings that started before the range: one more COQL (`Recurring_Activity is not null and Start_DateTime < start`). If COQL refuses it, the calendar still loads (note in `jpkCalendar.state.notes`).
- Chip names: one Accounts and one Contacts COQL by id. A What_Id that is not an Account gives no account chip (kept as `whatId`).
- Participants: `getRecord({Entity:'Events', RecordID})`, read only when a meeting is opened or the picker opens, only for today or the day on screen, cached, max `detailCap` (10) per day. Never for the week.

## Decisions and departures
- **Description and the passcode:** Description is read by COQL (fact of 22 Oct), used to find the join link, then dropped. The passcode, meeting ID and Description are never stored or shown. The join link keeps its own query string (Teams `?p=`, Zoom `?pwd=`), because removing it breaks one-click join; it only appears as a link target, never as text.
- **joinUrl:** the extractor returns `null` when none; the event field is `''` (step 5 interface). Teams `l/meetup-join` and `meet/<id>`, `teams.live.com/meet`, Zoom `/j/ /w/ /my/`, Google Meet `xxx-xxxx-xxx`; Outlook Safe Links are unwrapped. Meeting options, help, dial-in, download, register links are ignored. If Venue holds a URL, the venue shows "Zoom meeting" etc. instead of the URL.
- **getRecord fields:** the JS SDK's getRecord has no `fields` argument, so it reads the full record and keeps only `Participants`.
- **Write payload:** `{ id, What_Id: {id}, $se_module: 'Accounts', Who_Id: {id} }`, each part only when picked. `id` names the record and `$se_module` is required by Zoho with What_Id; nothing else is sent. `Trigger: ['workflow']` follows the page's `live.update`; set `jpkCalendarConfig.trigger = []` to skip workflows.
- **Write limit:** `jpkCalendarConfig.writeAllowedIds` (default `['6715134000009801001']`, `'*'` = all) is checked before any call; blocked writes say "Linking is limited to the test meeting while this is being checked." The flow is otherwise identical for every meeting.
- **Picker is inline in the calendar (non-modal `role="dialog"`), not a floating modal.** The frame is sized to its content, so a fixed modal would open in the middle of a tall frame, possibly off screen. Focus moves to its heading, Esc closes, focus returns to the opener (or the new chip when the opener is gone).
- **Details panel (new):** clicking a meeting title opens when, venue, repeat rule, attendees (lazy), link state, Join, Link, Open in Zoho, Open in Outlook. This is how "open a meeting" loads participants.
- **Cancelled:** titles starting "Canceled:" or "Cancelled:" are hidden (Events has no verified status field). Deleted records are not returned by COQL; a write to a meeting deleted since load shows Zoho's own error.
- **All-day (fixed after the live check of 22 Oct):** if the start string's own clock time is 00:00:00 (Outlook style), the dates are taken as written and a midnight end is exclusive. Otherwise the record is a UTC day written in another offset (live examples: "Kids no school" 2025-04-20T19:00:00-05:00 to 2025-04-21T18:59:59-05:00 = 21 Apr; "NAPSA Atlanta" 2025-09-13T19:00 to 09-17T18:59:59 = 14 to 17 Sep), so the UTC calendar dates of the start and end instants are used (an end at exactly 00:00:00 UTC is exclusive). The mode is decided by the start, so a local-midnight start with a 23:59:00 end keeps its written date. Never shifted by the viewer's zone; a multi-day all-day event is listed on each of its days. Tested with the exact live strings in Chicago and Los Angeles.
- **Recurrence:** DAILY/WEEKLY/MONTHLY with INTERVAL, BYDAY (ordinals in MONTHLY), BYMONTHDAY, BYSETPOS (MONTHLY), COUNT, UNTIL; wall time kept across DST (expanded in the viewer's zone). Anything else (YEARLY, BYHOUR...) is shown once on its record date and marked "Repeats. This repeat rule is not supported here...". Duplicates (same title and start) are dropped, records winning over expansions, in case Zoho also stores each occurrence as its own record (untested live).
- **Preview:** with no SDK or `?preview=1`, or `?caldemo=1|empty|err|later|done|slow`, the calendar reads built-in demo records through the same code, including the TEST event id; writes are simulated and say "Preview only: nothing was saved in Zoho."
